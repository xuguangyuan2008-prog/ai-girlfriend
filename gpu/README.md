# MiniMax H3 视频聊天：GPU 部署与提速

视频聊天模式（`/video.html`）的流程：用户发一句话 → 文本模型写台词和表情 → H3 在 GPU 上拍成一段几秒的视频 → 前端播放。
这份文档讲怎么在租用的 GPU 上部署 H3，以及针对「固定场景视频聊天」做了哪些提速。

## 1. 选卡

| 配置 | 说明 |
|---|---|
| **1 × H200 141GB**（推荐起步） | ref2va 主干网络（FP8 后约 33GB）和文本编码器（BF16 约 51GB）能同时放进显存，没有卸载开销 |
| 1 × H100 80GB | 需要 FP8，并把文本编码器卸载到 CPU（`serve.sh` 会自动判断），每条请求多一点文本编码时间 |
| 2 × H100 / H200 | `GPUS=2 bash serve.sh`，序列并行，单条请求更快；适合多人同时用 |

`--quantization fp8` 需要 Hopper（H100/H200）或更新的卡。

## 2. 安装与启动（在 GPU 机器上）

```bash
apt-get install -y ffmpeg                 # H3 处理素材需要 ffmpeg / ffprobe
pip install "sglang[diffusion]"
export HF_TOKEN=...                       # 首次启动会从 Hugging Face 下载 MiniMaxAI/MiniMax-H3
bash serve.sh                             # 默认端口 30000
```

`serve.sh` 只加载 ref2va 分区（`--model-variant ref2va`），开启 torch.compile 和 FP8。可调的环境变量写在脚本开头。

**安全**：不要把 30000 端口直接暴露到公网。用防火墙只放行 Web 服务器的 IP，或者用 SSH 隧道：
`ssh -N -L 30000:localhost:30000 gpu-host`，然后 Web 服务器上 `H3_BASE_URL=http://localhost:30000`。
如果前面加了带鉴权的网关，把 Bearer token 填到 `H3_API_KEY`。

## 3. 准备固定场景素材

放在 GPU 机器的 `/workspace/assets/`（或用 `H3_ASSET_DIR` 改目录）：

| 文件 | 要求 | 作用 |
|---|---|---|
| `anchor.png` | 9:16 竖图，就是视频画面本身：她在卧室里看着镜头、表情放松 | **每段视频的第一帧和最后一帧都钉在这张图上**：构图、光线、背景永远一致，片段之间、和待机视频之间无缝衔接 |
| `portrait.png` | **正方形**的脸部特写（可以从 anchor 里裁） | 长相参考。服务端会把参考图放大到短边 2048 再编码，正方形比 9:16 少约 44% 的 token |
| `voice.wav` | 6~10 秒、干净的人声，不要背景音乐 | 声音参考，保证每段视频是同一个声音。会被截断到视频时长，太长没用 |

制作建议：`anchor.png` 用任意文生图工具做成竖屏自拍风格；声音可以先用 H3 文生视频生成一段她说话的视频，满意后用
`ffmpeg -i clip.mp4 -vn -ac 1 voice.wav` 提取。场景描述写在 `server/videochat/prompt.js` 的 `scene`，要和 `anchor.png` 一致。

## 4. 预热、生成待机视频、压测（在 Web 服务器上）

```bash
# .env 里设置 H3_BASE_URL
npm run h3 -- warmup          # 每个时长档发一次请求，触发 torch.compile 编译（首次每档会比较慢）
npm run h3 -- idle            # 生成待机循环视频 → public/video/idle.mp4
npm run h3 -- say "哈哈，真的假的？快跟我说说！" --emotion surprised
npm run h3 -- bench --durations 4,6,8 --steps 8,16,30
```

`bench` 会输出每种「步数 × 时长」的首次耗时、稳定平均耗时，以及「等待时间 / 视频时长」。最后这个比值就是实际体验：
比如 2.0x 表示 6 秒的回复要等约 12 秒。

## 5. 提速措施

### 已经做了的

| 措施 | 原理 |
|---|---|
| **480p 竖屏**（`H3_SHORT_EDGE=480`, `9:16`） | 视频 token 约为默认 768p 的 40%，注意力的计算量下降更多 |
| **台词短 + 按长度选时长** | 台词编剧限制在 40 字以内；时长 = 朗读时间 + 留白，向上取到 4/6/8/10/12/15 秒档。大部分回复是 4~6 秒 |
| **固定时长档 + 预热** | torch.compile 按张量形状编译；只有几种时长，启动后预热一遍，请求时不会再临时编译 |
| **首尾帧钉在定妆照上** | 固定场景的关键。画面不会漂移，回复视频和待机视频首尾相接，切换时看不出接缝 |
| **正方形参考图** | 参考图 token 少约 44% |
| **FP8 量化** | 显存减半，矩阵乘更快 |
| **待机视频掩盖等待** | 等待时她在画面里安静地听、偶尔眨眼，前端显示「她在录视频… 已等待 / 预计时间」 |
| **素材放在 GPU 服务器本地** | 用路径引用，每次请求不用上传 |
| **无引导分支** | H3 是引导蒸馏模型，每步只算一次前向（没有 CFG 的双倍开销），这点 SGLang 默认就是 |

### 还要实测再决定的

| 措施 | 怎么试 | 注意 |
|---|---|---|
| **少步数加速 LoRA / FastH3** | `LORA=... bash serve.sh`，`H3_STEPS=8`；用 `bench --steps 8,16,30` 对比 | 默认 50 步，降到 8 步理论上快约 6 倍。**必须确认 LoRA 是为 ref2va 分区训练的**：H3 两个分区模块名相同，装错分区不会报错，但画质会变差。不用 LoRA 时 `H3_STEPS` 建议 20~30 |
| Cache-DiT 跳步 | `H3_QUALITY=high` | 官方在 4×H200 上测的 SSIM 0.931；步数已经很少时收益有限 |
| 两卡序列并行 | `GPUS=2 bash serve.sh` | 单条请求更快，成本翻倍 |

### 需要改 SGLang 才能做的（第二阶段）

- **跨请求缓存参考素材的编码结果**：H3 在 SGLang 里的处理阶段没有用通用的跨请求缓存，固定的参考图、声音、定妆照每次都会重新编码。场景固定，这部分完全可以只算一次。
- **调小参考图的编码分辨率**：2048 是写死的常量，调小能明显减少 token，但超出了官方训练和验证的分布，要看画质。

## 6. 质量风险（先实测）

- SGLang 源码里写明：**768 是 MiniMax 唯一公布过配方和参考输出的短边**，其它分辨率能生成，但画质和对提示词的遵循没有官方测量。480p 要先看效果，不行就退到 576 或 640。
- 中文对白的口型、发音质量，资料里没有找到专门的测评，要用自己的角色实测。
- H3 权重是社区许可证，部分地区（有报道称美国、欧盟、英国）不在授权范围内，商用前看清楚许可证。
