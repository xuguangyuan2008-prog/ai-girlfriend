# MiniMax H3 视频聊天：GPU 部署与提速

视频聊天模式（`/video.html`）的流程：用户发一句话 → 文本模型写台词和表情 → H3 在 GPU 上拍成一段几秒的视频 → 前端播放。

## 1. 两种模式

| | **快速模式**（默认，`MODE=fast`） | **一致性模式**（`MODE=ref`） |
|---|---|---|
| 模型 | 社区蒸馏的 [FastH3](https://haoailab.com/blogs/fasth3-preview/)（FastVideo） | 官方基础版 MiniMax H3 |
| 速度 | 4 次前向 + 90% 稀疏注意力，比基础版快约 14 倍 | 约 50 步，慢 |
| 实测数据（FastVideo 公布，768p，单张 B200，含编解码） | 5 秒视频 16.2s，10 秒 31.1s，15 秒 47.2s | 15 秒 678.7s |
| 能传的条件 | **只有文字**（FastH3 只蒸馏了文生视频） | 参考图 + 声音样本 + 首尾帧 |
| 长相 / 声音 / 场景一致性 | 靠固定的详细文字描述 + 固定种子，**会有一定漂移，需要实测** | 首尾帧钉在定妆照上、声音来自样本，最稳 |

先用快速模式跑起来，用 `npm run h3 -- consistency` 看漂移程度能不能接受，再决定后续方向（见第 6 节）。

## 2. 选卡

FastH3 和基础版的主干网络都是 33B 参数（BF16 约 66GB），文本编码器 BF16 约 51GB。

| 配置 | 说明 |
|---|---|
| **1 × H100 80GB**（够用） | `serve.sh` 会自动开在线 FP8（主干约 33GB）并把文本编码器卸载到 CPU。速度大约是 B200 的一半（估算，未实测） |
| **1 × B200**（更快） | 显存大，不用量化和卸载；FastVideo 的公开数据就是在 B200 上测的 |
| 多卡 | `GPUS=2 bash serve.sh` 序列并行，单条请求更快；FastVideo 报告 8 × B200 生成 15 秒视频只要 15.5s |

**延迟主要由算力决定，不是显存**：显存只决定能不能放下，速度看卡的算力和卡数。

## 3. 安装与启动（在 GPU 机器上）

```bash
apt-get install -y ffmpeg                 # H3 处理媒体需要 ffmpeg / ffprobe
pip install "sglang[diffusion]"
export HF_TOKEN=...                       # 首次启动会从 Hugging Face 下载权重
bash serve.sh                             # 快速模式，默认端口 30000
# MODE=ref bash serve.sh                  # 一致性模式
```

Web 服务器 `.env` 里的 `H3_MODE` 要和这里的 `MODE` 一致（默认都是 fast）。

**安全**：不要把 30000 端口直接暴露到公网。用防火墙只放行 Web 服务器的 IP，或者用 SSH 隧道：
`ssh -N -L 30000:localhost:30000 gpu-host`，Web 服务器上 `H3_BASE_URL=http://localhost:30000`。
前面加了带鉴权的网关的话，把 Bearer token 填到 `H3_API_KEY`。

## 4. 角色设定

**快速模式**：角色的长相、房间、声音全部写在 `server/videochat/prompt.js` 的 `scene` 里，每次请求一字不差地带上。
写得越具体（发型、衣服颜色、饰品、房间摆设、音色），不同片段之间越像同一个人。改完用 `consistency` 命令检查。

**一致性模式**额外需要 3 个素材，放在 GPU 机器的 `/workspace/assets/`（`H3_ASSET_DIR` 可改）：

| 文件 | 要求 | 作用 |
|---|---|---|
| `anchor.png` | 9:16 竖图，就是视频画面本身 | 每段视频的第一帧和最后一帧都钉在这张图上，画面永远一致，片段之间无缝衔接 |
| `portrait.png` | **正方形**脸部特写 | 长相参考。服务端会把参考图放大到短边 2048 再编码，正方形比 9:16 少约 44% 的 token |
| `voice.wav` | 6~10 秒干净人声 | 声音参考。会被截断到视频时长，太长没用 |

## 5. 预热、待机视频、测试（在 Web 服务器上运行）

```bash
npm run h3 -- warmup          # 每个时长档发一次请求，热身
npm run h3 -- idle            # 生成待机循环视频 → public/video/idle.mp4
npm run h3 -- consistency     # 同一种子、不同台词生成 4 段，拼成 media/consistency.png，看会不会「换人」
npm run h3 -- say "哈哈，真的假的？快跟我说说！" --emotion surprised
npm run h3 -- bench --durations 4,6,8 --edges 768,480
```

`bench` 的最后一列「等待 / 视频时长」就是实际体验：2.0x 表示 6 秒的回复要等约 12 秒。

## 6. 提速和一致性的选项

### 已经做了的

| 措施 | 说明 |
|---|---|
| FastH3（快速模式） | 4 次前向 + VSA 稀疏注意力 |
| 台词短 + 按长度选时长 | 台词限制在 40 字内；时长 = 朗读时间 + 留白，向上取到 4/6/8/10/12/15 秒档，大部分回复 4~6 秒 |
| 固定种子 | 相同的初始噪声，帮助不同片段保持相似的长相和构图 |
| 待机视频掩盖等待 | 等待时她在画面里安静地听，前端显示「她在录视频… 已等待 / 预计时间」 |
| 画面分辨率可调 | 默认 768（官方验证过的配置）；`H3_SHORT_EDGE=480` 视频 token 约少 60%，更快，但画质官方没测过，用 `bench --edges 768,480` 对比 |

### 快速模式下长相或声音漂移明显时

FastH3 不能传参考素材，所以一致性要靠后处理补：
- **声音**：生成后对音轨做一次声音转换（voice conversion），转成固定的音色。只换音色、不改节奏，口型仍然对得上；5 秒音频在 GPU 上处理不到 1 秒。
- **长相**：逐帧换脸到固定角色，会额外增加几秒。
- 或者等社区出 ref2va 的蒸馏版本。FastVideo 的说明里提到，Ref2VA 用的是单独的参考分支，需要单独蒸馏。

### 一致性模式提速（需要改 SGLang 或等社区）

- 少步数 LoRA：`LORA=... MODE=ref bash serve.sh`，`H3_STEPS` 调小。**必须是为 ref2va 分区训练的 LoRA**：H3 两个分区模块名相同，装错分区不会报错，但画质会变差。
- 跨请求缓存参考素材的编码：H3 在 SGLang 里的处理阶段没有用通用的跨请求缓存，固定素材每次都会重新编码。

## 7. 风险

- FastH3 模型卡说明：复杂动作、细节和部分音频质量可能低于基础版；中文对白的口型和发音没有找到专门测评，要用自己的角色实测。
- 480p 不是官方验证过的分辨率（SGLang 源码里写明只有 768 有官方配方和参考输出）。
- 在 80GB 卡上自动开的 FP8 量化和 FastH3 的组合没有公开测评，画质不满意可以用 `QUANT=none` 换大显存卡对比。
- H3 权重是社区许可证，部分地区不在授权范围内，商用前看清楚许可证。
